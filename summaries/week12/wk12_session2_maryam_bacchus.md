### Voyager: An Open-Ended Embodied Agent with Large Language Models

#### Problem Addressed
The issue that arose was that traditional reinforcement learning (RL) agents, while they were capable of mastering specific tasks, when they learned something new, they would overwrite or degrade what they had learned before. Even the best RL agents of the time were trained on fixed task distributions, so they couldn't generalize or adapt when the goals or environment changed. In an open ended world like Minecraft, with endless possibilities, agents could not adapt. The proposal was that instead of training an agent with gradient-based RL, you could use an LLM to reason about what to do next, write executable code to do it, and then store that code as a reusable skill, essentially building a growing library of capabilities that compounds over time.

#### State of Related Works
At the time of this paper, there were two main approaches to building agents in Minecraft. The first was RL based agents, which operated on low level primitive actions (move forward, attack, jump) and struggled with systematic long horizon exploration. These agents needed massive amounts of environment interaction and still failed to generalize beyond specific tasks they were trained on. The second category was early LLM based agents like ReAct, AutoGPT, and BabyAGI, which demonstrated that LLMs could be used for high level planning and task decomposition. The problem with these approaches was that they had no persistent memory of what they had learned, and each episode started fresh. An agent that solves the problem of "craft a wooden pickaxe" in episode one has no way to reuse that knowledge in episode two. They also typically operated with text only representations, making them poorly suited for environments where you need to actually execute actions in a physical simulation.

#### Proposed Solution and Key Insights
The researchers proposed Voyager, a lifelong learning agent built on top of GPT-4 that operates through three integrated components. The first is an automatic curriculum. Instead of the researchers manually specifying what tasks the agent should attempt, GPT-4 dynamically proposes the next task to pursue based on the agent's current state (what items it has), what biome it's in, what has already been accomplished. The second component is a skill library. Whenever the agent successfully completes a task, the code it used to do so gets stored in a library (vector database), indexed so it can be retrieved later. This directly addresses catastrophic forgetting because the skills live outside the model weights as they're stored externally in a database. The third component is an iterative prompting mechanism. When GPT-4 generates code to execute a task, that code runs in the Minecraft environment, and any errors, environment state changes, or failed conditions are fed back to GPT-4, which then revises the code. GPT-4 also does self-verification after each completed task to confirm the objective was actually achieved before moving on. The key insight that makes all of this work is the choice to use code as the action space rather than low level commands. Code is composable, interpretable, and temporally extended where a single function call can represent a multi-step behavior like "craft an iron pickaxe" without having to specify every individual action.

It was found that Voyager outperformed all baselines. It obtained 3.3x more unique items than the next best approach, traversed 2.3x more distance in the game world, and reached tech tree milestones like the diamond pickaxe 15.3x faster. On zero-shot generalization tasks, where a new Minecraft world was created and the agent was asked to complete specific goals it had never seen, Voyager solved 15 of 15 tasks using skills retrieved from its library, while baselines solved none or close to none.

#### Drawbacks and Limitations
Because it never finetunes any model weights, it avoids the costs of training but pays a significant API cost for every GPT-4 call—the automatic curriculum, skill generation, and self, verification all require separate calls. The skill library also grows without pruning, and there's no mechanism to detect when a skill has become outdated or is conflicting with another.

#### Future Directions
Currently the agent reads game state through text APIs rather than raw pixels. Future work could look at incorporating vision models into the Voyager architecture.



### SWE-bench: Can Language Models Resolve Real-World GitHub Issues?

#### Problem Addressed
GitHub Copilot had millions of users, and benchmarks like HumanEval were regularly cited as evidence of how capable these models had become. The issue that arose was that these benchmarks were becoming saturated and, more importantly, didn't reflect what a software engineer actually does. HumanEval and MBPP present self-contained problems that can be solved in a few lines of code given a clean function signature and a handful of unit tests. Real software engineering is nothing like that. A real GitHub issue might say "this function behaves incorrectly when the input is an empty list" and require you to trace that bug across multiple files, understand the broader architecture, modify the right lines without breaking anything else, and then verify your fix passes all existing tests. The researchers proposed that the only honest way to measure progress in code models was to give them the same problems that real developers are solving every day which are actual GitHub issues from real, production codebases.

#### State of Related Works
At the time of this paper, the dominant coding benchmarks were HumanEval, MBPP, DS-1000, and CodeContests. These were all well constructed, but they shared a common design assumption, that the problem is self-contained and can be solved in isolation. Models were evaluated by generating a function and running it against a fixed test suite, which worked well for measuring whether a model could write syntactically correct and logically sound code for a narrow problem. But none of these benchmarks required the model to reason about a pre-existing codebase, navigate across files, understand interdependencies between modules, or interact with a runtime environment to check whether something worked. There was a growing concern in the community that models could ace these benchmarks while still being essentially useless at the kinds of tasks engineers spend most of their time on.

#### Proposed Solution and Key Insights
The researchers built SWE-bench by crawling pull requests and issues from 12 popular Python repositories, including Django, Flask, scikit-learn, and sympy, and then filtering for pull requests that were linked to a reported issue and modified at least one test file. By requiring that each PR changed a test file, the authors guaranteed that there was a concrete, signal for correctness - tests that failed before the PR was merged and passed after. They call these "Fail-to-Pass" tests. Each task instance is set up inside a Docker container with the repository installed at the exact commit just before the pull request was applied. The model receives the issue description and the codebase, and must produce a patch that makes the Fail-to-Pass tests pass without breaking anything else. The benchmark ended up with 2,294 task instances and was accompanied by two retrieval strategies for giving models relevant context from the codebase: BM25 retrieval, which uses keyword matching to pull in relevant files, and "Oracle" retrieval, which cheats by using the actual files modified in the real pull request. They also fine-tuned CodeLlama on SWE-bench training data to create SWE-Llama as a specialized baseline.

Claude 2, one of the strongest models at the time, resolved just 1.96% of issues. GPT-4 with oracle retrieval—meaning it was given the exact files it needed to edit, resolved only 1.74%. SWE-Llama with oracle retrieval managed 12.47%, the best of any tested approach. These numbers made it immediately clear that passing HumanEval at 80%+ accuracy doesn't come close to meaning a model can do real software engineering.

#### Drawbacks and Limitations
The benchmark is limited to Python repositories, which means it misses the kinds of issues that arise in systems programming, JavaScript ecosystems, or multi-language codebases.

#### Future Directions
Extending the benchmark to non-Python languages is an obvious next step.
